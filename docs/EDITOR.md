# DanmakuForge 弹幕锻坊 — 编辑器实现文档

> 目标：把 `.brg`（SlimeStorm 弹幕工程）作为**工程侧的关卡数据源**来可视化编辑，
> 而不是在 SlimeStorm 里选点位、再手工抄进临时脚本。
>
> 本文件是**编辑器实现文档**（架构 / 保真规格 / 踩坑与教训）。
> 快速上手与命令行见 [`../README.md`](../README.md)；`.brg` 格式见
> [`BRG_FORMAT.md`](BRG_FORMAT.md)；预览所用运行时快照见 [`../VENDOR.md`](../VENDOR.md)。
>
> 下文把最终消费 `.brg`、同时提供那份运行时实现的那套工程统称为**目标工程**；
> 本工具与它解耦，只通过 `.brg` 文件打交道。

---

## 1. 为什么不是「重造 SlimeStorm 的编辑器」

SlimeStorm 自带编辑器已经实现了结构树、画布拖拽、属性栏、时间轴（手册 §5.8）、
事件编辑器（§5.6/5.7）、关联副本（§4.8）。**重造一个通用编辑器没有意义。**

真正的缺口是：SlimeStorm 的编辑器**不懂工程侧的工作流** —— 看不到工程的贴图与预烘焙档、
自机判定半径真值、单弹压制 sidecar，也没有保真层（改一次就可能抹掉它不认识的字段）。
所以 DanmakuForge 的定位是**弹幕工作台**：只管好 `.brg` 文件这一层，
把「改弹幕 → 存回工程目录 → 运行侧生效」这条路走到最稳。

它与目标工程解耦：独立的源码树、独立的主场景、独立的 exe。两边之间只剩「读写同一批
`.brg` 文件」这一层契约，外加 `VENDOR.md` 里那份运行时快照，保证预览与运行侧跑出
同一条弹道。

## 2. 核心架构决策：双层模型 ⚠️ 最重要

```
BrgDocument（保真层，唯一真相源）        BrgLoader + BrgPlayback（语义层）
  ├ 完整 XML 树，含不认识的标签            ├ 只用于播放/预览
  ├ 改字段 = 定点改文本                    ├ 只读，永不回写
  └ save() → 除改动外逐字节不变            └
        ▲
   结构树 / 画布 gizmo / 属性面板 全部只经由 BrgDocument 修改
```

**为什么必须这样**：`BrgLoader` 只解析 146 种标签里的 **72 种**，另有 **74 种完全没读**
（每个发射器都有的 `Velocity`/`Direction`/`Accelerate`/`AccDirection`、`BindingID`、
`DeepBinding`、`Blend`、`Ghosting*`、`Twinkle*`、`BackImage*`、`Region`/`VisualSize`、
`Reflect*`、`ParaA`/`ParaB`、`ScaleX`/`ScaleY`、`Affect`、`MotionLink` …）。

> **如果拿 `BrgLoader` 的数据类当模型再存回 XML，会静默抹掉近一半字段。**

所以编辑器改的每一处都走 `BrgDocument`；`BrgLoader` 只负责把树翻译成可播放的语义。

## 3. 保真规格（已验证：139/139 逐字节一致）

写回必须严格满足下面 6 条，否则 SlimeStorm 会报「XML 文档(N,C)中有错误」：

| # | 规格 |
|---|---|
| 1 | UTF-8 **无 BOM** |
| 2 | **CRLF** 换行；**结尾无换行符** |
| 3 | **2 空格**缩进；根元素 `<Barrage>` **无缩进** |
| 4 | 头部 `<?xml version="1.0"?>` 与 `<Barrage xmlns:xsi=… xmlns:xsd=…>` **原样保留**（ElementTree / XMLParser 都会丢弃未被引用的 xmlns 声明，所以按原文提取、不重建） |
| 5 | **固定元素顺序**：`EmitterBullet` 93 字段、`EventData` 20 字段（C# XmlSerializer 语义） |
| 6 | 空元素写**自闭合**形式 `<X />`（斜杠前一个空格） |

规格由 `tools/proto_brg_roundtrip.py` 在全部 139 个真实 `.brg`（684 个发射器 /
2687 个事件）上反推，`tools/check_brg_order.py` 统计出权威顺序。

## 4. 两条已确认的硬约束

### 4.1 删除的两层语义：发射器（A）与单弹压制补丁（B）

`.brg` **没有「单颗子弹」这个实体**：子弹是运行时按 `Way`/`Circle`/`Count` 每帧
程序化生成的，XML 里不存在、也无法表达「第 1234 号子弹」。SlimeStorm 编辑器自己的
快捷键表写的也是 `Del = 删除选中发射器`（手册 3.2.3），最接近的「影响器 + 指定 ID」
仍然只到**发射器**粒度。

所以删除分两层：

- **语义 A（P0）**：`Del` 删**发射器（弹幕团）**，直接改 `.brg`，SlimeStorm 完全兼容。
- **语义 B（P2b）**：**单弹压制补丁**。每颗弹的身份 = `发射器序号:出生帧:该帧内第几发`
  （无论是否被压制序号都照常自增，否则压一发会让后面所有弹身份前移、补丁错位）。
  编辑器里「删除单弹」拾取最近的一颗弹记入压制表，存成 sidecar
  **`<xxx.brg>.patch.json`——`.brg` 本体一个字节不动**，SlimeStorm 仍能正常打开。
  运行侧在创建 `.brg` 播放器时自动 `load_patch()`，所以压制是**真实玩法修改**，
  不只是预览效果。工具栏：删除单弹（点选）/ 撤销压制 / 清空压制 / 存压制。

### 4.2 确定性预览

预览复用 `BrgPlayback` + `BulletManager`，改字段后从第 0 帧**固定种子重放**到当前帧
（`seed(fixed_seed)`，与 `Replay.gd` 同款做法）。已实测同一 `.brg` 连跑两次输出
**逐字节相同**，所以拖拽参数时的画面是可复现的。

## 5. 用法

```powershell
# 在本仓库根目录执行（$GODOT = Godot 4.7.x 可执行文件）

# 启动编辑器（可带一个 .brg）
& $GODOT --path . -- --open "D:\cards\my_card.brg"

# 打开即自动播放（截图/调试用；不带的话截图停在帧 0，没有子弹）
& $GODOT --path . -- --open "<file.brg>" --play

# 发布版等价：build\DanmakuForge.exe --open "<file.brg>" --play
```

也可以直接在 Godot 编辑器里打开 `res://scenes/DanmakuForge.tscn` 按 F6。

### 画布 gizmo 与**直接拖拽**（P1）

选中发射器后会出现 4 类手柄，**拖哪个就改哪个属性**，拖拽时属性面板数值**实时跟随**：

| 手柄 | 形状 | 改的属性 |
|---|---|---|
| 本体 | 圆 | `Position`（跟随宿主）或 `EmitPoint`（绝对发射点） |
| 箭头端点 | 方形 | `EmitDirection`（发射角度，按住 **Shift** 吸附 15°） |
| 扇形两条边 | 圆形 ×2 | `Range`（以发射角度为中心对称张开） |
| 半径圆上的点 | 方形 | `EmitRadius` + `RadiusDirection` |
| 侧向菱形 | 菱形 | `Way`（条数）：离发射器越远条数越多（`Way = 1 + round((距离-34)/8)`），旁边实时标 `Way N` |

- **范围用「相对拖拽」**：按下时记录当时的范围与角差，之后只施加**增量**。
  这样 `Range = 360`（满环，两个手柄会重合在正后方）时向内拖也不会一跳到底。
  满环时手柄刻意放在 `基准 ± 90°`，既可见又能分辨拖的是哪一侧。
- 「指向自机」（`-99999`）的发射器**不显示方向手柄** —— 那个角度运行时才算得出来，
  不该被静态拖拽覆盖；但**范围手柄照常可用**（Range 只是一个对称张角）。
- 手柄**最后绘制**：标签底板是不透明深色块，先画手柄会被选中的发射器自己的标签盖住。
- **吸附网格**：工具栏「吸附」勾选后，拖本体改 `Position`/`EmitPoint` 时吸附到 **60px** 网格
  （与画布网格线一致）。默认关闭，精确微调不受影响。

### 自机小球（体验自机狙）

画布底部有一个可操纵的青色小球（标「自机」）——它就是**自机狙的瞄准基准**：
`EmitDirection` / `RadiusDirection` 为哨兵 `-99999` 时，运行时按「发射点 → 小球」算角度。

- **大小 = 运行侧真实判定点**：内芯青色 = 圣洁态半径 `Sanctity.HIT_R_SANCTITY`（2.0），
  外圈红色 = 污染态半径 `Sanctity.HIT_R_CORRUPTION`（3.0），旁边标 `r2.0/3.0`。
  这样在编辑器里估弹缝与实机一致，不会因为球画大了/小了误判。
- **拖动小球**，或让画布持有焦点后按 **方向键 / WASD**（220 px/s）移动。
  （抓取用 16px 的隐含范围，仅方便点中这颗很小的球，不参与判定。）
- 移动**不触发重放**：播放层每帧发射时实时读取小球位置，所以新发射的自机狙会**追着小球飞**；
  已发射的弹保持原方向（与运行侧语义一致）。
- 拖动/属性编辑预览时用了小球当前位置；固定种子重放仍确定（重放期间小球静止）。

### 时间轴（P1）

| 操作 | 效果 |
|---|---|
| 拖片段本体 | 改 `StartTime` |
| 拖片段右边缘红线 | 改 `Duration` |
| **多选**后拖片段 | **整组**一起移动（统一 delta，最左不越过第 0 帧） |
| **多选**后拖右边缘 | **整组**统一改时长（`Duration=0` 不限时长的片段跳过） |
| 点片段 | 选中该发射器（与结构树 / 画布联动） |
| 标尺点击 / 拖动 | 移动播放头并重放预览 |
| 右键片段 / 空白 | 弹出「复制选中 / 粘贴」菜单 |
| `Ctrl+C` / `Ctrl+V` | 复制 / 粘贴选中发射器（新 ID，`Tag` 加 `_copy`） |
| `Ctrl` + 滚轮 | 缩放（以鼠标为锚点）；缩放后**停止自动适配** |
| `Shift` + 滚轮 / 中键拖动 | 横向平移 |
| 滚轮 | 纵向滚动轨道 |
| 「适配」按钮 / `F` | 整段铺满可视宽度（并恢复自动适配） |

`Duration = 0` 在 `.brg` 里表示「不限时长」，片段会画到右端并标注 `∞`。
**机制**：未手动缩放时，时间轴尺寸一变就自动重新适配（`_auto_fit`）——
这是必须的，见 §6.2 的坑 1。

### 事件编辑器（P1）

「事件…」按钮打开，**内嵌**在主窗口里（`gui_embed_subwindows`），单窗口操作。

- 打开时**自动切到有事件的那一侧**（发射器事件 `EventGroupList` / 子弹自身事件
  `BulletEventGroupList`），否则一打开就是空列表
- 事件组：新增 / 删除 / `Loop` / `LoopCircle`
- 事件列表：新增 / 删除 / 上下挪动；每行列成 `条件 → 结果 变化方式 值`
- 事件字段：`Mode` / `contype` / `opreator` / `conditionValue` / `changemode` /
  `changetype` / **结果属性** / `res` / `changetime`
- 界面里直接写着语义提示：**每帧检测条件，满足就执行**（`Equal` 一次性；
  `Greater`/`Less` 每帧重放、`Increase` 逐帧累积）

⚠️ **两个必须守住的格式约束**（都在 `BrgDocument` 里集中处理）：

1. **`changename` 数字 ID 必须与 `ChangeName*` 字符串一致**——不一致事件空转，
   且 SlimeStorm 报「XML 文档(N,C)中有错误」。所有写操作都走
   `BrgDocument.set_event_result()`，它同时写两者（属性下拉里显示 `名称 (id N)`）。
2. **即便 `Mode=Bullet`，`ChangeNameEmitter` / `ChangeNameAffecter` 也必须填合法成员**，
   否则照样报错。新建事件时三个字段都写成各自枚举的第 0 项。

### 快捷键

| 快捷键 | 功能 |
|---|---|
| `Del` / `Backspace` | 删除选中发射器（语义 A） |
| `Ctrl+S` / `Ctrl+O` | 保存 / 打开 |
| `Ctrl+Z` / `Ctrl+Shift+Z` / `Ctrl+Y` | 撤销 / 重做 |
| `Ctrl+A` | 全选发射器 |
| `Ctrl+C` / `Ctrl+V` | 复制 / 粘贴选中发射器（时间轴右键菜单同款） |
| `Ctrl+T` | 显示 / 隐藏时间轴 |
| `F` | 时间轴适配整段 |
| `空格` | 播放 / 暂停 |

**播放固定 60fps**：本工程关了 vsync（`project.godot` 的 `window/vsync/vsync_mode=0`），
而编辑器 `_process` 是**每渲染帧**触发一次；若直接「每渲染帧推进 1 逻辑帧」，播放会以
渲染帧率（关 vsync 时可能几百 fps）狂跑，看起来「极快」（按住/拖动窗口时才接近正常）。
所以播放走**真实时间累加器**：按 `1/60 s` 累加推进逻辑帧（卡顿后最多补 30 帧），与渲染
帧率彻底解耦。实测同样 6 秒延迟，帧号 3642 → **351**（≈60fps）。

**拖拽落点写到哪**：发射点为「跟随发射器自身」哨兵（`-99998`）时改 `Position`
（相对宿主偏移），否则改 `EmitPoint`（绝对坐标）。状态栏会提示当前是哪种。

**批量修改**：多选后改属性会同时写入全部选中项（对齐 SlimeStorm 手册 §4.8）。

**窗口与缩放**：逻辑排版尺寸固定 `1580×1240`，用 Godot 的 `canvas_items` 拉伸整体缩放
（`content_scale_aspect = KEEP`）。这样**输入坐标由引擎自动换算**，不必自己处理
缩放后的鼠标映射。窗口会自动贴合屏幕可用区域；启动时会打印一行
`逻辑 1580x1240 → 物理 WxH（缩放 N.NN×）`，分辨率不匹配是**可见**的，而不是让用户
觉得「字怎么这么小」。本机实测屏幕可用 `3200×1904` → **1.00×**，无需缩放。

### 6.2 靠截图 + 实测数字发现的 P1 bug

### 6.3 为什么拖动时不做实时重放

实测分解（37 发射器 / 300 帧）：**序列化 27 ms + 解析 28 ms + 模拟 175 ms ≈ 230 ms**。
每帧做一次必然卡死。因此：

- gizmo **每帧都跟手**（`queue_redraw` 不受影响）
- 弹幕重放**防抖 140 ms**：连续拖动期间不重放，停手/松手后重放一次
- 弹池从 8192 降到 `PREVIEW_CAPACITY = 4096`、并关掉编辑器用不到的
  空间哈希（`BulletManager.collision_enabled`），池满是会给「⚠ 弹池满」提示

> `BulletManager` 为此新增了两个变量（`capacity` / `collision_enabled`），**默认值等于
> 原来的常量 `true`/`MAX_BULLETS`，运行侧行为完全不变**——已在目标工程侧用运行时自检
> 与机器人回归确认（峰值弹数、残机均与基线一致）。
> 注：机器人结果本身**不是逐次确定的**（同参数两次 kills 30 / 29），
> 所以回归对比要看 `max_bullets` 这类结构性指标，不要看 kills。

> **环境前提（本机已配置）**：要让我能读截图，`C:\Users\15263\.dsh\settings.yaml`
> 里 `hypercharmland` 的 `deepseek-v4.1-flash` 条目必须声明多模态输入——
> 补上 `input: [text, image]`（该模型本身是多模态，只是默认没声明）。
> 备份在 `settings.yaml.bak-before-vision`。
